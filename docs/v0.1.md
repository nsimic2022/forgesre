# ForgeSRE V0.1 — Implementation architecture

**Status:** active for V0.1 implementation  
**Date:** 2026-08-20  
**Supersedes in V0.1:** Go core, React SPA, Caddy ingress, bundled NetBox, discovery worker

This document compares the Phase 0 proposal (`docs/architecture.md`) with the V0.1 implementation task and records the stack we are actually building.

---

## 1. Comparison

| Topic | Phase 0 proposal | V0.1 task | Decision |
|---|---|---|---|
| Goal | Full architecture, no runtime | Working vertical slice on `./install.sh` | **Implement V0.1 slice now** |
| Core language | Go | Python / FastAPI preferred | **Python 3.12 + FastAPI** so the operator can debug it |
| CLI / install | Go binary + bash wrappers | Bash | **Bash** (`install.sh`, `doctor.sh`, `backup.sh`, `update.sh`, `forgesre`) |
| UI | React SPA embedded in Go | Simple web UI, not a design exercise | **Jinja2 templates + small vanilla JS** (no Node build) |
| Ingress | Caddy | Not required | **No Caddy in V0.1.** Core publishes the product port; Grafana has its own port |
| Profiles | Minimal / Standard / Full AI | Standard + Full AI | **Standard and Full AI only** |
| NetBox / Discovery | Standard overlay | Explicitly V0.2 | **Omit.** Local assets + seeded demo asset. Provider field reserved in config |
| AI | Five in-process agents | One Investigation Agent | **One agent.** Architecture still allows more later |
| LLM | llama.cpp container | Local container or existing endpoint; CPU-small default | **OpenAI-compatible client.** Bundled llama.cpp if a model is present; otherwise honest builtin analyst on real evidence |
| Email | External SMTP | External SMTP, no Postfix | Unchanged |
| Compose | One file, profiles | Docker Compose required | Unchanged |
| Repo layout | `cmd/` + `internal/` | `backend/` `frontend/` `agents/` `monitoring/` `logging/` `scripts/` | **V0.1 layout** (operator-requested) |

The Phase 0 principles still hold: smallest working system, reuse Prometheus/Loki/Grafana, AI is read-only, no fake UI, no extra brokers.

---

## 2. Why Python, not Go

The operator maintains and debugs this system and asked for Python and Bash. That is a material constraint. A single-binary Go CLI is nicer for air-gap ops later; V0.1 optimizes for **readability and debuggability**.

Core still runs in Docker. The host still only needs Docker, Compose, Bash, and Git. Python dependencies live in the image, not on the host.

---

## 3. V0.1 stack

| Piece | Choice |
|---|---|
| API + UI | FastAPI, SQLAlchemy 2, Jinja2 |
| DB | PostgreSQL 16 |
| Metrics | Prometheus + Alertmanager |
| Logs | Loki + Grafana Alloy (tail Core log file; no Docker socket) |
| Dashboards | Grafana (datasources provisioned; not 100 dashboards) |
| AI | `agents/investigation.py` — read-only, data ForgeSRE already fetched |
| LLM | Optional compose service `llm` (llama.cpp OpenAI API) or `ai.llm.url` |
| Notifications | In-process SMTP client |
| Auth | Session cookie, bcrypt, five roles |

V0.1 uses **host networking** on a single Linux host. That keeps DNS and published ports out of the way: Core and Grafana listen on the host, Prometheus/Loki/Alertmanager bind localhost. Bridge networking remains possible later; it is not required for the appliance.

No Redis, no Caddy, no NetBox, no Postfix, no agent microservices.

---

## 4. Vertical slice (must work)

```
install wizard → login → demo asset → Prometheus metrics → alert
  → Alertmanager → incident → Loki logs → investigation/RCA
  → playrule → playbook → generated email → doctor → backup
```

`./forgesre demo` (and `scripts/demo.sh`) seeds that path so a developer sees it in minutes.

---

## 5. Reserved for later (do not build in V0.3)

V0.3 implements the RCA foundation (`docs/v0.3.md`). Still later: SNMP discovery suite, bundled NetBox, Code Agent, Open WebUI, HA, Kubernetes, Slack/Teams/SMS/tickets, Visual Agent graph engine.

---

## 6. Risks

| Risk | Mitigation |
|---|---|
| LLM image/model too heavy for CPU/demo | Builtin analyst uses **real** metrics/logs; UI labels the provider honestly |
| Alert `for:` too long for a demo | High CPU rule uses `for: 10s`; demo also posts the webhook so the UI does not wait |
| Docker socket for Alloy | **Not used.** Alloy tails a log volume |
| Port 3000 busy | Preflight; Grafana port is configurable |
| Fake-looking UI | Every screen is backed by API models and live integrations |

---

## 7. Implementation order

1. Config contract + compose + monitoring/logging config  
2. Core API + DB + auth + seed  
3. UI pages  
4. Prometheus/AM webhook → incidents + evidence  
5. Investigation agent  
6. Playrules/playbooks/escalation/notifications  
7. Wizard, doctor, backup, update, demo  
8. Tests + local install + e2e  

V0.2 (NetBox, discovery, larger RCA) waits until this spine works. See `docs/v0.2.md` for the discovery/inventory slice.

---

## 8. What V0.1 actually ships

Implemented and exercised on a Linux Docker host:

- `./install.sh --non-interactive` wizard writes `.env`, `config/forgesre.yml`, `secrets/secrets.env`
- Login, RBAC, audit
- Demo asset `forge-demo-01`
- Prometheus scrapes Core (CPU/memory/disk/demo gauge); HighCPU alert
- Alertmanager webhook creates/updates ForgeSRE incidents
- Loki + Alloy tail Core logs; incident evidence collector queries both
- Investigation agent (builtin analyst on real evidence; optional llama.cpp if a GGUF is present)
- Playrules / playbooks / escalation / generated email notifications
- `./forgesre demo`, `./doctor.sh`, `./backup.sh`

Not in this slice: bundled LLM weights, Postfix, React/Go, Caddy, bundled NetBox. Discovery and external NetBox landed in V0.2.
